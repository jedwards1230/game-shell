# tv-shell v2 — the shell

> **Status:** spike · 2026-09-07 · `shell-v2/`, built beside `shell/` and wired into
> nothing. v1 still boots the couch and is untouched. This document records the
> decisions the spike makes, the two repo rules it reverses, and — as prominently
> as the rest — what it does **not** prove.
>
> It answers the first half of [`V2_DESIGN.md`](V2_DESIGN.md) §13 Q1 (the runtime)
> and the shell half of §13 Q12 (repo layout). Q1 is not closed — that waits on
> today's shell running against the shim under gamescope, a separate, user-gated
> step. What **is** settled is the shim's necessity: post-map tagging was measured
> on the deployment on 2026-09-07 and does not work (§8a).

## 1. What this is

A minimal Qt Quick application that exists to prove three things under gamescope:
**it maps, it self-tags its X11 atoms before it maps, and it takes controller
focus.** Everything visible is placeholder — coloured rectangles, no theme, no
data. Everything structural is not: this spike sets the patterns every later
screen follows, so the parts worth reviewing are the shapes, not the pixels.

| Piece | File | What it establishes |
|---|---|---|
| Pure role → atoms | `shell-v2/src/surfacetags.{h,cpp}` | The tagging contract as a pure function. No Qt GUI, no X, in its link line. |
| The X layer | `shell-v2/src/x11tagger.{h,cpp}` | The **only** place the shell speaks X, mirroring `core/src/atoms.rs`. |
| The typed toplevel | `shell-v2/src/surface.{h,cpp}` | `Surface` declares a **role**; the role drives the tagging, before map. |
| Focus decisions | `shell-v2/qml/TvShell/focusGraph.js` | Declarative focus graph, pure, headlessly tested. |
| Focus glue | `FocusRouter.qml`, `FocusSlot.qml` | A slot declares where it sits; the router computes neighbours. |
| Placeholder screen | `Main.qml` | Three separate toplevels; a D-pad grid; a live disable-a-cell toggle. |

## 2. Layout: `shell-v2/`, beside `shell/`

Same precedent as `core/` beside `daemon/`: a new tree, a new build, v1 unaffected
and still buildable. `shell/` is not touched by this PR and is not ported by it.

`V2_DESIGN.md` §13 Q12 left the v2-`shell/` half open pending Q1's runtime answer,
and named no directory. `shell-v2/` is that directory.

## 3. Runtime: a plain Qt Quick **application**, not the `qml` runtime

§13 Q1 framed the choice as Quickshell-on-xcb versus the plain `qml` runtime, and
measured the latter working under gamescope at 4K120. The spike takes a third
position, and the reason is a finding rather than a preference:

**The shell cannot be a plain `qml` invocation, because the pre-map ordering has
no hook that QML can reach.** Section 5 below sets that out. The moment a C++ type
is required, a build step is required, and once there is a build step, owning
`main()` costs nothing and buys the startup checks (platform-plugin warning, one
place to set application identity). So:

- **Not Quickshell.** Its headline feature is layer-shell, which does not exist
  under gamescope; §13 Q1 already records that choosing it buys nothing the plain
  runtime lacks and carries unmeasured xcb risk. Nothing in this spike changes
  that, and nothing in it forecloses revisiting it either — the tagging shim is a
  `QQuickWindow` subclass, which Quickshell could not use as-is, but the pure
  layers (`surfacetags`, `focusGraph.js`) are runtime-agnostic.
- **Not the bare `qml` runtime.** See §5.

**The premise is measured; the runtime choice is not yet.** That a C++ type is
needed at all rests on two independent legs, both now established: gamescope
requires the properties in place before the window maps (measured, §8a), and Qt
provides no virtual hook to put them there (§5). What remains open is §13 Q1's own
question — today's shell running against this shim under gamescope on the pinned
build. Until that runs, this is the right answer for the reason given, not a
finished one.

## 4. One QML module, one URI

v1 has **eleven** `qmldir` registries and **69** relative-directory imports
(`import "../"` ×26, `import "../components"` ×17, …). Adding a type there means
picking a registry, and reaching a type means knowing how many levels up you are.

v2 has one module, `TvShell`, generated by `qt_add_qml_module`. There is no
hand-written `qmldir`, no relative-directory import anywhere, and no second module
to add a type to. Every QML file in the shell says `import TvShell` and every type
resolves. This is enforced by construction rather than by review: a new file is
added to `QML_FILES` in one `CMakeLists.txt` or it does not exist.

## 5. The pre-map tagging shim

### What it sets, and when

`V2_DESIGN.md` §5, "Shell windows self-tag". Per role, as 32-bit `CARDINAL`
properties:

| Role | Properties | Purpose |
|---|---|---|
| `Base` | `STEAM_GAME=<appid>` | The shell as an app; a base-layer candidate. |
| `Overlay` | `STEAM_OVERLAY=1`, `STEAM_INPUT_FOCUS=1` | Drawer / QAM: takes keyboard and mouse **without** displacing the base layer. |
| `Toast` | `STEAM_OVERLAY=1`, `STEAM_NOTIFICATION=1` | Notifications; deliberately **no** `STEAM_INPUT_FOCUS`. |

The app id defaults to **9001** — the id the measured prototype uses
(`dev/gamescope/launch.sh`), overridable with the same `TV_SHELL_GS_SHELL_APPID`
env var — and never 769, which under `--steam` is the Steam client's own id and
carries gamescope's `window_is_steam` behaviour.

Two rules in that table are load-bearing and easy to "tidy" wrongly, so both have
their own test:

- **An overlay carries no `STEAM_GAME`.** Tagging it with the shell's app id would
  make it a base-layer candidate — precisely the bug the separate-toplevel design
  exists to prevent.
- **A toast carries no `STEAM_INPUT_FOCUS`.** A notification that takes keyboard
  focus is a notification that steals the pad mid-game.

The sequence is:

```
setVisible(true)  ->  create()      X CreateWindow
                  ->  applyTags()   X ChangeProperty
                  ->  base impl     X MapWindow
```

All of it on the xcb connection Qt's platform plugin already owns, so the server
processes the property writes before the map **by protocol guarantee, not by
timing**. Opening a second connection would have made "tagged before map" a race.

### The finding: Qt has no virtual hook between create and map

The obvious implementation is to override `QWindow::setVisible`. **It is not
virtual in Qt 6** — nor is `create()`, and there is no other virtual called
between window creation and map. This constrains any Qt-based v2 shell, Quickshell
included, so it is recorded here rather than buried in a comment.

`Surface` therefore enforces the ordering at the entry points that do exist, and
deletes the ones it cannot control:

- `visible` is **redeclared** as a `Q_PROPERTY` on `Surface`. QML resolves
  properties through the meta-object and finds the derived one, so a
  `visible: true` binding goes through this class.
- `Surface::setVisible` **hides** the base slot, so C++ calls through a `Surface *`
  go through this class.
- `show()`, `showNormal()`, `showFullScreen()`, `showMaximized()` are **deleted**.
  Each calls the base `setVisible` non-virtually and would map an untagged window;
  deleting them turns a silent bug into a compile error.

Visibility is additionally **deferred to `componentComplete()`**, the way
`QQuickWindowQmlImpl` defers it for `Window`. Without that, a `Surface` whose
`visible: true` appeared above its `role:` in the QML body would map before the
role was assigned — correctness by declaration order, which is the class of
fragility this design exists to remove.

**Residual gap, stated plainly:** a caller who upcasts to `QWindow *` and calls
`setVisible(true)` there still bypasses the shim. Nothing in the shell does, and
the deleted `show()` family closes the accident-shaped paths, but this is a
convention at the C++ level rather than a guarantee. If it ever bites, the fix is
to stop inheriting `QQuickWindow` publicly and wrap it instead.

### Roles, not flags

A caller sets `role`, never atoms; there is no API for tagging an arbitrary
window. That is what makes "an overlay accidentally drawn inside the base window"
unrepresentable: an overlay is not a flag on a surface, it **is** a separate
`Surface` with role `Overlay`. §5's requirement that drawer, QAM and toasts be
separate toplevels is therefore structural.

`Main.qml` declares the three as **siblings** of a non-visual root rather than as
nested `Window`s, because a `Window` declared inside a `Window` acquires a
transient parent (`WM_TRANSIENT_FOR`), which is a different thing to gamescope
than an independent toplevel.

## 6. The focus model

### What it replaces

v1's focus contract is eight duck-typed members — `previousRow`, `nextRow`,
`firstRow`, `lastRow`, `canFocus`, `regionFocused`, `focusFirstChild`,
`ensureVisibleRequested` — hand-wired across ~17 files with no compile-time check.
Every "focus stranded" bug in that codebase was a mis-wired neighbour, and a
mis-wire was invisible until it was on a television.

### In three sentences

A component declares **where it sits** — a `(row, column)` cell and whether it is
focusable right now — and never who its neighbours are. A router computes the
neighbour on every move from the **live** set of cells, so there is no stored
pointer that can go stale and no wiring to get wrong. If the cell under focus
stops being focusable, the router re-homes to the nearest survivor, so stranding
is reachable only when there is nothing at all to focus.

### The rules, and the mutations that confirm each is defended

Stated in `focusGraph.js` and asserted in `tests/qml/tst_focusgraph.qml`. Each was
verified by **breaking the rule and watching the suite go red** — a green suite
proves nothing until you have seen it fail.

| Rule | Mutation applied | Result |
|---|---|---|
| **R1** Vertical movement skips rows with no focusable cell | `neighbour` considers only `from.row ± 1` | caught |
| **R2** No wrap in any direction | horizontal search falls back to the far end of the row | caught |
| **R3** A non-focusable cell is never returned | the `focusable` filter is removed | caught |
| **R4** `rehome` lands somewhere whenever anything is focusable | `rehome` gives up unless a survivor is in the same row | caught |
| Overlay carries no app id | `Overlay` gains `STEAM_GAME` | caught |
| Toast is input-inert | `Toast` gains `STEAM_INPUT_FOCUS` | caught |
| Base carries the app id | `Base` returns no tags | caught |
| **Tags land before the map** | `applyTags()` moved AFTER `QQuickWindow::setVisible(true)` | caught |

The last row is the one this PR turns on, and it needed a real X server, so it was
run on a throwaway branch through CI rather than on a workstation with no `Xvfb`.
`premap` failed on all three roles with the intended message — *"STEAM_GAME was
set AFTER the window mapped (property at 3, map at 2) — gamescope had already
decided"* — and the other two lanes stayed green, so the failure was the ordering
and nothing else.

**R5** — neighbours are derived from coordinates alone — is structural rather than
assertable: there is no field in a cell that could name another cell.

The pre-map ordering assertion (`tst_premap`) needs a real X server, so both its
pass and its mutation were verified in CI rather than on a workstation with no
`Xvfb`.

### Where the decisions live

`focusGraph.js` is a `.pragma library` with no QML in it. That is the one v1
pattern carried forward deliberately — pure decision modules, QML as glue — and it
is expanded here rather than merely preserved: the router contains no branch that
is not a call into it.

## 7. Verification

Three lanes, in increasing order of what they need:

| Lane | Needs | What it asserts |
|---|---|---|
| `surfacetags` | nothing | The role → atoms mapping, per role, plus the two negative rules. |
| `qml` | nothing (offscreen) | `focusGraph.js` directly, **and** a real `FocusRouter` over real `FocusSlot`s. |
| `premap` | a real X server | `PropertyNotify` arrives **before** `MapNotify`, per role. |

The `premap` lane is opt-in behind `TV_SHELL_TEST_XVFB` — the same shape `core/`
uses — and `.github/workflows/shell-v2.yml` **sets that variable**, so it executes
rather than silently skipping. A dedicated step asserts all three lanes were
registered, because jedwards1230/tv-shell#469 was exactly the failure of a gated
leg wired to nothing: a gate that skips silently is indistinguishable from a gate
that passed.

`premap` does not read the property back after the window is up — that would prove
the property exists, not that it existed in time. It watches from a **second X
client**: `create()` first (which deliberately does not tag), then subscribe to the
window, then `setVisible(true)`, then assert the event order. Move `applyTags()`
after the base `setVisible()` and it fails every time, not sometimes.

The QML lane **links the real `TvShell` module** rather than assembling a copy of
the production files the way v1's `tests/qml/run.sh` must. There is no copy step
and therefore no drift.

## 8. What this spike does **not** prove

A spike that cannot fail is not a spike. In descending order of how much it would
hurt to be wrong:

1. **This code has not run under gamescope.** The *contract* it implements is
   measured — post-map tagging does not work, and a scoped launch is a focus
   candidate untagged (§8a) — but that was measured with the kit's clients, not
   with these windows. Whether `shell-v2` maps, is tagged in time, and takes the
   pad is still unobserved. The hardware spike is a separate, user-gated step, and
   it is what closes §13 Q1.
2. **The `Toast` pair is unverified.** `STEAM_OVERLAY` + `STEAM_NOTIFICATION`
   together is this spike's reading of §5's prose; the prototype exercised only the
   `Overlay` pair. If gamescope treats a notification differently, `surfacetags.cpp`
   and its test are the two files that change.
3. **Three sibling toplevels are asserted, not observed.** That they map as three
   independent windows and that the overlay takes input without displacing the base
   layer are §5 claims; nothing has watched gamescope do it with *these* windows.
4. **The focus model has never met a controller.** It is exercised by synthetic
   key events offscreen. The pad path (core → uinput → Qt) is untouched here.
5. **Deferred visibility interacts with `Loader`.** Every real screen will be
   loaded lazily; a `Surface` created inside a `Loader` gets `componentComplete()`
   at a different moment, and that has not been exercised.
6. **The residual upcast gap in §5** is a convention, not a guarantee.
7. **`Surface` gives up what QML's `Window` provides.** It subclasses
   `QQuickWindow`, not `QQuickWindowQmlImpl` (which is private API), so the
   conveniences QML's `Window` adds on top — `visibility`, screen handling, the
   `Window` attached property — are not inherited. Nothing in the placeholder
   needed them; a real screen might.
8. **Qt version drift.** Developed against Qt 6.11 locally, gated in CI at 6.8.3.
   The couch's Qt is a third number. `Q_PROPERTY` shadowing and
   `QNativeInterface::QX11Application` are both stable API, but "stable" is not
   "measured on the deployment".

## 8a. Why the shim is necessary — measured, not argued

This section began as an open fork: the shim's whole premise is that post-map
tagging is too late, yet `V2_DESIGN.md` §5 *also* has the core tagging windows
post-map as its "tag as repair" rule, and both could not be unconditionally true.
Either post-map tagging works — in which case the core could tag the shell's
windows too, the plain `qml` runtime would suffice and this build step would be
unnecessary complexity — or it does not, in which case the shim is right and the
repair path is broken.

**It was measured on 2026-09-07, on the deployment, against the pinned build. The
second branch is the true one: post-map tagging does not work.** Two independent
sources agree.

**1. The bench, 2026-09-06, gamescope 3.16.28** (pinned up from 3.16.23 that day,
jedwards1230/homelab-ansible#321). Already recorded in `dev/gamescope/lib.sh`:

```
launch                                   GAMESCOPE_FOCUSABLE_WINDOWS
plain launch, post-hoc tag attempted     (empty)
plain launch, control                    (empty)
inside app-steam-app9003-2970.scope      8388625, 9003, 2998
```

The scoped launch became a focus candidate with **no tagging at all** —
`STEAM_GAME` was never set — and the display went to `fps=120.000000 /
focus=9003`. Both unscoped launches produced no focus candidate, tagged or not.
Note the version detail: post-hoc tagging *used to* appear to work, and stopped at
3.16.28. Anything that depended on it was depending on tolerance, not contract.

**2. A live control against the running v2 session, 2026-09-07.** An unscoped,
untagged `xmessage` mapped, its process confirmed alive, and never entered
`GAMESCOPE_FOCUSABLE_WINDOWS`, which stayed on Moonlight's triplet throughout.

**The mechanism.** gamescope resolves a window's app id at window **creation**,
from the pid the X server reports via `XRes`, by
`sscanf(cgroup, "app-steam-app%u-%d.scope", …)` in `src/Utils/Process.cpp`. A
property arriving after `MapNotify` has missed the decision — there is nothing in
that path that re-reads it.

### What follows for this PR

**The shim is justified by measurement, not only by the Qt finding in §5.** Those
are two independent legs: gamescope requires the properties to be in place before
the window maps, and Qt provides no virtual hook to put them there. The first says
the ordering matters; the second says enforcing it costs a C++ type. Together they
make §9.1's build-tooling reversal forced by evidence rather than argued from Qt
internals — and they retire the "why not just have the core do it" question, which
would otherwise have been the first thing asked of every later screen.

### What follows for the core

The other half of the fork is a real defect, filed as
**jedwards1230/tv-shell#472** — the core's "tag as repair" path cannot work as
specified. `dev/gamescope/lib.sh` had independently spotted the same
chicken-and-egg on the kit side ("`gs_tag_pid` DISCOVERS candidate windows through
`GAMESCOPE_FOCUSABLE_WINDOWS`, so with that atom empty it can never find a window
to tag").

**Not fixed here, deliberately.** It lives in `core/` and correcting
`V2_DESIGN.md` §5 belongs to #472; this PR keeps its zero-files-touched-in-`core/`
property. Read #472 for the detail rather than this section.

## 9. Two repo rules this reverses

Both are stated here rather than slipped in, and both are edited in the same PR.

### 9.1 "No build tooling" now scopes to v1's `shell/`

`CLAUDE.md` said, as a design constraint: *"No build tooling: no bundler, no
compiler, no package manager for QML. Files are deployed as-is."*

That is no longer true of v2's shell, and it cannot be — a conclusion that now
rests on measurement rather than on reading Qt's headers. gamescope resolves a
window's app id at creation and never re-reads it, so the properties must be in
place before the window maps (measured 2026-09-07, §8a); QML cannot issue
`XChangeProperty`; Qt exposes no virtual hook between window creation and map
(§5). A C++ type is therefore required, and CMake follows from it. `V2_DESIGN.md`
§13 Q1 anticipated exactly this ("a C++ helper or plugin") while the repo's stated
rule still said otherwise, which would have left the first person to read both
with a real contradiction.

`CLAUDE.md` is amended in this PR to scope the rule to v1's `shell/`, where it
remains true and remains valuable — v1's shell is still interpreted, still deployed
as-is, and still the thing that boots the couch on a rollback.

### 9.2 v2's shell is not rsync-deployable

v1's deploy cycle is `git pull` on the target plus a `systemctl --user restart` —
possible only because QML is interpreted at runtime. v2's shell is a compiled
binary with its QML embedded in the binary's resources, so:

- Pulling a branch on the device changes nothing until it is **built** there or a
  built artifact is shipped to it.
- `docs/INSTALL.md`'s and the `tv-shell-dev` skill's "sync files, restart
  Quickshell" loop does not apply to `shell-v2/`.
- The agent-native dev loop's `dev_deploy` → `restart_shell` becomes
  `dev_deploy` → **`dev_build`** → `restart_shell`, which is the shape the daemon
  already uses.
- Whether the device builds or consumes a release artifact is the same question
  `tv-shell-input` already answers with a `semver:input:*` release stream, and it
  is likely to get the same answer.

**Not solved here.** No install script, no unit, no packaging change is in this PR.
It is written down so that the first person to try `git pull` on the box knows why
nothing changed.

## 10. Building it

```bash
cmake -S shell-v2 -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build
cmake --build build --target all_qmllint
ctest --test-dir build --output-on-failure

# with the X-backed lane (needs an X server):
Xvfb :99 -screen 0 1280x800x24 &
TV_SHELL_TEST_XVFB=:99 cmake -S shell-v2 -B build -G Ninja
cmake --build build && ctest --test-dir build --output-on-failure
```

`TV_SHELL_TEST_XVFB` is read at **configure** time: without it `ctest` reports two
lanes, with it three.
